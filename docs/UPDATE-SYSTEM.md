# مشخصات سامانهٔ به‌روزرسانی — Update System

**هدف:** اعمال نسخهٔ جدید از طریق پنل، با نمایش درصد پیشرفت و خطاها — بدون نیاز به SSH.

---

# ۱. اصل امنیتی — دو جزء کاملاً جدا

**اپلیکیشن اصلی هرگز نباید به Docker یا سیستم‌عامل میزبان دسترسی داشته باشد.**

اپلیکیشن اصلی رو به اینترنت است، ورودی کاربر می‌گیرد، و فایل آپلود می‌پذیرد. اگر روزی آسیب‌پذیری
در آن پیدا شود، مهاجم نباید بتواند به میزبان برسد.

```
┌─────────────────────────────────┐      ┌──────────────────────────────┐
│  Aqsat.Api  (رو به اینترنت)      │      │  Aqsat.Updater  (جدا)        │
│                                  │      │                              │
│  پنل به‌روزرسانی — فقط UI        │─────▶│  • pull ایمیج امضاشده        │
│  نمایش وضعیت و پیشرفت           │ mTLS │  • پشتیبان‌گیری دیتابیس       │
│                                  │◀─────│  • اجرای مهاجرت              │
│  ❌ بدون دسترسی Docker           │      │  • جابه‌جایی کانتینر          │
│  ❌ بدون دسترسی FS میزبان        │      │  • health check + rollback   │
└─────────────────────────────────┘      │  ✅ فقط این یکی Docker دارد  │
                                          │  ❌ به اینترنت باز نیست       │
                                          └──────────────────────────────┘
```

`Aqsat.Updater`:
- روی شبکهٔ داخلی، **بدون پورت عمومی**
- فقط از `Aqsat.Api` با mTLS یا توکن مشترک درخواست می‌پذیرد
- API بسیار محدود: `GET /status` · `POST /update` · `POST /rollback` · `GET /progress/{id}`
- **هیچ ورودی دلخواهی نمی‌پذیرد** — فقط یک برچسب نسخه از فهرست مجاز

---

# ۲. قواعد غیرقابل مذاکره

۱. **فقط نقش `Platform.Owner`** — این نقش متعلق به شماست، نه هیچ نمایندگی. کاربران نمایندگی
   این صفحه را اصلاً نمی‌بینند.

۲. **احراز هویت دومرحله‌ای اجباری** برای شروع به‌روزرسانی. رمز عبور کافی نیست.

۳. **فقط بستهٔ امضاشده.** هر نسخه با کلید خصوصی شما امضا می‌شود؛ Updater قبل از اعمال، امضا و
   هش را بررسی می‌کند. **بستهٔ بدون امضای معتبر، رد می‌شود.** این تنها چیزی است که جلوی نصب
   نسخهٔ دستکاری‌شده را می‌گیرد.

۴. **پشتیبان‌گیری کامل قبل از هر مهاجرت — بدون استثنا.** اگر پشتیبان‌گیری شکست خورد، به‌روزرسانی
   شروع نمی‌شود.

۵. **حالت تعمیر (maintenance mode)** قبل از شروع. کاربران فعال ۶۰ ثانیه هشدار می‌گیرند.

۶. **بازگشت خودکار** اگر health check بعد از استقرار رد شود.

۷. **همه‌چیز در لاگ تغییرناپذیر** — چه کسی، چه نسخه‌ای، چه زمانی، نتیجه.

۸. **پنجرهٔ زمانی مجاز.** به‌روزرسانی فقط در ساعات کم‌مصرف (پیش‌فرض ۲ تا ۶ بامداد) مگر با
   تأیید صریح «اضطراری».

## بررسی پیش‌نیازها (مرحلهٔ ۱)

قبل از هر کاری این‌ها چک می‌شوند و اگر یکی رد شود، **به‌روزرسانی اصلاً شروع نمی‌شود**:

- فضای دیسک آزاد ≥ ۲ برابر حجم دیتابیس
- اتصال به مخزن ایمیج
- سلامت دیتابیس
- نبود جاب Hangfire در حال اجرا
- نبود کاربر فعال با کار ذخیره‌نشده (هشدار، نه توقف)
- سازگاری نسخه (نمی‌شود از ۱.۰ مستقیم به ۳.۰ رفت)

# ۴. مدل داده

```
UpdatePackage
  Id, Version, ReleaseNotes (fa), ImageTag, Sha256, Signature,
  MinimumFromVersion, HasDbMigration bit, IsSecurityUpdate bit,
  PublishedAt, IsYanked bit

UpdateRun
  Id, PackageId, FromVersion, ToVersion,
  StartedByUserId, StartedAt, CompletedAt,
  Status (1=running 2=success 3=failed 4=rolledback),
  CurrentStage, ProgressPercent,
  BackupPath, BackupSizeBytes,
  ErrorCode, ErrorMessage, ErrorDetail (nvarchar(max))

UpdateStageLog
  RunId, StageNo, StageName, StartedAt, CompletedAt,
  Status, Output (nvarchar(max))
```

**نکته:** این جداول در دیتابیس اصلی‌اند ولی `AgencyId` ندارند — سطح پلتفرم‌اند نه نمایندگی. باید
از RLS مستثنا شوند (یا `AgencyId` تهی با سیاست جداگانه).

# ۶. بازگشت (Rollback)

## خودکار

اگر health check بعد از استقرار رد شود → بازگشت به ایمیج قبلی، خروج از حالت تعمیر، ثبت خطا.

## دستی

دکمهٔ «بازگشت به نسخهٔ قبل» تا ۷ روز فعال است.

## ⚠️ محدودیت مهم — این را جدی بگیرید

**بازگشت ایمیج آسان است. بازگشت مهاجرت دیتابیس نیست.**

اگر مهاجرت ستونی را حذف یا داده‌ای را تبدیل کرده باشد، برگرداندن ایمیج کافی نیست — باید پشتیبان
بازگردانی شود، و **هر تغییری که کاربران بعد از مهاجرت انجام داده‌اند از بین می‌رود.**

**سه قاعده برای نوشتن مهاجرت‌ها:**

۱. **مهاجرت‌ها همیشه رو به جلو و سازگار با نسخهٔ قبل باشند.** ستون جدید nullable، ستون قدیمی
   بلافاصله حذف نشود.

۲. **حذف ستون در دو نسخه انجام شود:** نسخهٔ N استفاده از آن را قطع می‌کند، نسخهٔ N+1 حذفش می‌کند.
   بین این دو، بازگشت بی‌خطر است.

۳. **مهاجرت مخرب، تأیید جداگانه بخواهد** با متن صریح: «بازگشت از این نسخه نیازمند بازگردانی
   پشتیبان است و داده‌های بعد از به‌روزرسانی از بین می‌رود.»

---

# ۷. حالت تعمیر

- کاربران فعال ۶۰ ثانیه قبل، از طریق SignalR هشدار می‌گیرند: «به‌روزرسانی تا ۶۰ ثانیهٔ دیگر —
  کارتان را ذخیره کنید»
- درخواست‌های جدید → صفحهٔ تعمیر با زمان تخمینی
- کارهای Hangfire متوقف می‌شوند (جاری تمام می‌شود، جدید شروع نمی‌شود)
- `Platform.Owner` همچنان دسترسی دارد
- خروج خودکار پس از health check موفق
- **سقف زمانی:** اگر بیش از ۱۵ دقیقه در حالت تعمیر ماند، بازگشت خودکار

---

# ۸. مسیر انتشار نسخه — سمت شما

```
تسک تمام شد
    ↓
تست خودکار پاس شد
    ↓
build ایمیج با برچسب نسخه
    ↓
امضا با کلید خصوصی
    ↓
push به مخزن
    ↓
ثبت UpdatePackage با یادداشت تغییرات فارسی
    ↓
انتشار مرحله‌ای:  محیط آزمایشی → ۱ نمایندگی → ۱۰٪ → همه
```

**انتشار مرحله‌ای مهم است.** اگر همهٔ نمایندگی‌ها روی یک سرورند، یک به‌روزرسانی معیوب همه را
همزمان زمین می‌زند. حداقل یک نمایندگی داوطلب برای نسخهٔ اول داشته باشید.

**Yank:** اگر نسخه‌ای معیوب بود، `IsYanked` را روشن کنید تا به بقیه پیشنهاد نشود.

# ۹. آنچه ساخته نمی‌شود

- ❌ **آپلود فایل دلخواه به‌عنوان بسته** — فقط از مخزن امضاشده
- ❌ **اجرای دستور دلخواه از پنل** — حتی برای «عیب‌یابی»
- ❌ **ویرایش تنظیمات میزبان از پنل**
- ❌ **به‌روزرسانی خودکار بدون تأیید** — همیشه انسان تأیید کند
- ❌ **دسترسی نمایندگی به این پنل** — حتی فقط‌خواندنی

# ۱۱. یک جایگزین ساده‌تر که ارزش بررسی دارد

اگر تعداد نمایندگی‌ها کم است و همه روی یک سرور، شاید **Watchtower** یا یک اسکریپت ساده کافی باشد
و این سه تسک لازم نباشد.

**ولی از لحظه‌ای که چند سرور یا چند مشتری سازمانی دارید، این پنل ضروری می‌شود** — چون شما
نمی‌توانید برای هر به‌روزرسانی به هر سرور SSH بزنید.

**پیشنهاد:** تسک ۱۹ تا ۲۱ را بعد از رسیدن به ۲۰ مشتری بسازید، نه قبلش. تا آن موقع، استقرار دستی
با یک اسکریپت کافی است — و شما یک مسیر امنیتی حساس را زودتر از لازم باز نکرده‌اید.
